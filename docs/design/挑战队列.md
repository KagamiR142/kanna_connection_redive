# 挑战状态推断算法

> 代码：`challenge/`、`clanbattle/model.py`（监控循环内调用）

## 目标

在【状态】/ 申请成功回复中展示「某 Boss 当前有哪些人在挑战」，包括未走平台申请的 **未知玩家**。

---

## 数据可靠性

| 来源 | 可靠性 |
|------|--------|
| 用户上报（申请/取消/sl/掉刀） | 高，依赖主动 |
| `damage_history` 结算 | 高，确定性 |
| 「过去 1 分钟人数」接口 | **上升沿可信，下降沿不可用** |

该接口是 1 分钟滑动窗口，只统计「开始挑战」时间点；人数下降可能是窗口老化，不代表玩家离开。详见 [platform.md](平台需求.md) 及 backup 设计文档 §2.2。

---

## 双轨制

1. **已知申请名单**：`申请出刀` 即入列，不等进本确认  
2. **进入信号计数器**：纯数字，记录「已检测进本、尚未被结算/sl/掉刀消耗」的次数

```
未知玩家数 = max(0, 进入信号 − 已知申请人数)
```

展示为「未知玩家 A/B/C…」。

---

## 事件处理

| 事件 | 已知申请 | 进入信号 |
|------|----------|----------|
| 申请出刀 | +1 | 不变 |
| 取消申请（未进本） | −1 | 不变 |
| 接口人数上升 +Δ | 不变 | +Δ |
| 接口人数下降 | 不变 | **忽略** |
| sl / 掉刀 | −1 | −1 |
| 结算到账 | 匹配则 −1 | **总是 −1** |
| Boss 击杀 | 清空 | 清零 |

### 报刀推送中的队列展示

监控自动报刀在组装消息时，**先于** `on_settlement` 读取申请队列，并统一经 `build_damage_push_challenger_lines`：

- 列表与 `目前有{n}人正在挑战` 的 `n`：**结算前**队列行数，经统一入口**始终排除当前出刀者**，仍含未知玩家行（不依赖 `on_settlement` 是否清队）
- 当 **`enter_signal`**（进本信号）大于 0 且 **小于** `n` 时，标题为 `目前有{n}人正在挑战（Boss内{k}人）：`，`k` = `enter_signal`；下方仍列出全部申请与未知行（申请成功、进本提醒等场景）
- **进本上升沿**：`{boss}王当前有{y}人出刀，申请队列中有{z}人：` + 换行 + 挑战者列表；`y` = `enter_signal`（上升沿后），`z` = 列表行数
- **接口 `fighter_num`**：游戏侧为近一分钟挑战人数等指标，会随时间下降；监控**仅上升沿**累加 `enter_signal`，下降沿**不**减 `enter_signal`。展示用 `enter_signal`，不用镜像 `fighter_num`
- **sl / 掉刀**：`on_self_report` 使 **enter_signal −1**，与 `Boss内{k}人` / 进本 `{y}` 一致
- **报刀推送**：组装在 `on_settlement` **之前**；`Boss内{k}人` 的 `k` 取 `max(0, enter_signal − 1)`（本刀出刀者视为已离 Boss；击杀为 `0`），与随后 `on_settlement` 扣减一致
- 击杀时 `on_settlement` 清空全队发生在报刀文本生成**之后**；非击杀不会清空全队申请
- 申请成功、进本上升沿等其它场景仍用 `build_challenger_text_lines`（不排除出刀者）

合刀线 `@` 名单与上述排除规则一致，见 [合刀线提醒](合刀线提醒.md)。

---

## 设计取舍

- 甲申请了但未进本，坏玩家先进并结算：甲的申请 **保留**（不误删）
- 无申请时坏玩家进本：显示未知玩家直至结算或 Boss 死
- 接口抖动不会误报未知玩家（下降沿不处理）
